# AgentFlow contract suite

Black-box tests that pin down what the AgentFlow backend does **as seen from outside**: the UI's
HTTP API and `/api/ws`, the agent API that `flowctl` calls, `flowctl` itself, and the files an agent
run reads and writes. The Python backend passes them today. The Rust rewrite (`app/`, see
`docs/desktop-app-investigation.md`) has to pass the same tests before it replaces `backend/`.

The black-box suite only starts processes, sends HTTP requests and reads files, so any
implementation that honours the contract below can be tested. `test_chat_goldens.py` is a
separate Python reference check: it imports pure renderers to detect drift in frozen Slack
outputs. Rust consumes those outputs in `core/tests/chat_render.rs`; no Slack SDK is started.
There are 117 recorded cases. Rust's chat service/transport tests also use a real localhost
WebSocket and fake HTTP/terminal adapters; they do not establish authenticated Slack acceptance.
The per-name migration inventory is generated by `python contract/audit_chat_tests.py`;
use `--check` to reject drift or pending local tests. All 126 applicable local Python chat test
functions have named Rust counterparts. See
[the inventory](../docs/evidence/slice-6-chat-test-inventory.md) for the two deferred live-provider
functions and one inapplicable Python optional-import test.

## Running

From this directory, with the backend's venv (it has `pytest`, `httpx` and `websockets`):

```sh
../backend/.venv/Scripts/python -m pytest            # Windows; bin/python on macOS/Linux
../backend/.venv/Scripts/python -m pytest test_flowctl.py -k rust   # one module / filter
```

Each module starts its own backend with a fresh data directory, worktree directory and
configuration on a free port, using the stub agent (`scripts/stub_agent.py`) for every role. The
Python target needs `git` and `zellij` on PATH. A full run takes several minutes.

| Variable | Effect |
|---|---|
| `CONTRACT_TARGET` | `python` (default) or `rust` |
| `CONTRACT_PYTHON` | Python used for the stub agent and the Python target (default: the one running pytest) |
| `CONTRACT_RUST_BIN`, `CONTRACT_RUST_FLOWCTL` | Rust binaries (default: `app/target/{release,debug}/agentflow.exe`, `flowctl.exe`) |
| `CONTRACT_RUST_TERMINAL` | `embedded` (default) or `zellij` for the Rust target |
| `CONTRACT_STUB_FLOWCTL` | flowctl the stub agent calls, e.g. the Rust binary against the Python backend |
| `CONTRACT_UPDATE_GOLDEN` | `1` re-records `golden/` (Python target only); review the diff before committing |
| `CONTRACT_KEEP` | `1` keeps each backend's temp directory for inspection |

`test_flowctl.py` runs every test once per flowctl implementation: the Python module always, and
the Rust binary when it is built (`cargo build` in `app/`).

## What is covered

| Module | Contract |
|---|---|
| `test_auth.py` | `/api/health`; browser pairing (single-use code, local UI origin only); session cookie that survives a restart; origin check on human mutations; trusted Host header; `/api/ws` auth and pushed task snapshots |
| `test_config.py` | `/api/config` (shape golden) and its edits: default repository (exact bytes written to config.json), exchange rate, cost controls and billing modes; reload refusals; harness listing and re-detection; directory browsing (root-constrained too); the diagnostic log's access rules; X-Request-ID |
| `test_chat_config.py` | offline Slack field validation and reload refusal, startup/pairing with no operator, and continued API availability; recorded against Python first, with no Slack connection |
| `test_tasks.py` | create (worktree, branch, harness cwd, node list), duplicate and invalid repository, listing, validate-repository, cancel, archive/unarchive, delete preview and delete, running a node |
| `test_built_ui.py` | actual Vue build at the API origin, history routes, byte-identical assets, HEAD, missing assets, API pairing and Host checks; requires `npm run build` in `frontend/` |
| `test_agent_api.py` | the run directory (prompt, scoped credential), credential scoping to task and run, agents refused human actions, question/answer round trip, completion, late callbacks, failure reports |
| `test_flowctl.py` | arguments, messages and exit codes; credential and run-id rules; pending-complete.json for replay (byte format included); submission.json cleanup; BOM tolerance; live question → running → status → complete → fail; incremental `finding`s used by a bare reviewer completion; `exited` failing the node |
| `test_workflow.py` | discovery with a question → requirements approval → implementation → both reviews → fix iteration (finding responses, prior-finding rulings) → final verification → READY_FOR_PR; the review-iteration cap |
| `test_workers.py` | bounded parallel workers, queue dispatch, dependency merges, ownership rejection, idempotent completion and integration through local Git |
| `test_pr_tracking.py` | manual PR-created/merged controls, undo, URL validation and late callbacks |
| `test_jira.py` | localhost HTTPS Jira picker, attachment download at creation, architect re-sync, prompted generation and guarded status transition; uses the installed Git OpenSSL on Windows |

### Golden files (`golden/`)

- `shapes/*.json`: the structure (keys and value types) of key responses, so the UI's
  `frontend/src/api/types.ts` keeps holding. Values are not compared.
- `prompts/<role>/<NN>.md`: the prompt each agent run of the full workflow receives, with paths,
  the Jira key, SHAs, run ids and the API port replaced by placeholders. Agents follow these files
  literally, so their text is part of the contract.

A deliberate change to a response or prompt in the Python backend means re-recording the goldens
and making the same change in the Rust port.

The prompt goldens were recorded on Windows and contain native `\` paths, so they won't match a
macOS/Linux run. Record a per-platform set before running the suite there.

Shape checks are exact, except that `null` is accepted for the few fields a background job fills in
(`SET_BY_TIMING` in `golden.py`).

### Goldens for modules the HTTP suite can't reach yet

`record_python_goldens.py` is not a test: it imports `agentflow` to record what Python does with
configuration and the database (`golden/config`, `golden/db`) and the exact bytes of the task
workspace files (`golden/workspace/<platform>`, kept byte-exact by `.gitattributes`), and generates the Rust schema
(`app/crates/core/src/db/schema.rs`). `cargo test` in `app/` checks the port against them. Run it
after changing `config.py` or the models, with a kept full-workflow database for the populated
fixture:

```sh
backend/.venv/Scripts/python contract/record_python_goldens.py <temp>/agentflow-contract-python-*/home/agentflow.db
```

## Startup contract for a backend binary

A target is started as `<binary> --config <file> --port <port> --skip-jira-check` and must:

- read the `config.json` format the Python backend reads (`config.example.json`);
- print `AgentFlow browser pairing code: <code>` on stdout once it accepts pairing;
- answer `GET /api/health` with `200 {"ok": true, "version": "<string>"}` without authentication;
- write a `flowctl` shim (`flowctl.cmd` on Windows) into its bin directory and put that directory
  on the PATH of every agent it launches, along with `AGENTFLOW_API`, `AGENTFLOW_TASK`,
  `AGENTFLOW_AGENT`, `AGENTFLOW_RUN`, `AGENTFLOW_CREDENTIAL_FILE`, `AGENTFLOW_TASK_DIR`,
  `AGENTFLOW_WORKTREE` and `AGENTFLOW_FLOWCTL`;
- launch the configured harness command with the prompt reference as its last argument, and deliver
  a human's answer to an agent's question as a line on the agent's terminal input;
- exit when terminated, and not leave agent processes behind.

## Not covered yet

- Authenticated live Jira/GitHub/Slack/model behavior, complete Slack callback and ask lifecycle
  parity, usage accounting and budgets beyond the current task/workflow checks, recovery after a
  restart mid-run, and the terminal stream endpoint. The embedded and zellij targets both pass
  the present suite; that does not cover every terminal-specific lifecycle.
- Event-log traces: event messages are checked loosely (`Task created`, `READY_FOR_PR`), not as a
  golden sequence, because concurrent reviews make their order vary.
